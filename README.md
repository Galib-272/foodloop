# FoodSphere AI — Food Waste Zero

AI-assisted food rescue platform: surplus forecasting, donation management, recipient matching, collection tracking and impact analytics.

## Run it

Requires **Node.js 22.5+**. The database uses Node's built-in SQLite, so there are no native packages to install.

```bash
npm install
npm run dev          # http://localhost:3000
```

On first start the app creates `data/foodsphere-v2.db` and seeds demo data. The two demo donors' sales history is **real rows from the Kaggle food-waste dataset** (dates shifted to end yesterday); donations, organizations and users are fictional. To reset, stop the server and delete the `data/` folder.

## Architecture

| Layer | Where |
|---|---|
| Public site | `app/page.tsx`, `components/landing`, `app/(about, guidelines, privacy, …)` |
| App (role dashboards) | `app/app/**` — sidebar filtered by role in `lib/nav.ts`; every page and API checks the role on the server |
| REST API | `app/api/**` (PRD §21 routes) — consistent `{ error: { code, message, fields } }` responses |
| Domain services | `lib/donations.ts` (status workflow + transactions), `lib/matching.ts`, `lib/analytics.ts`, `lib/forecast.ts`, `lib/csv.ts`, `lib/admin.ts` |
| Database | `lib/db.ts` (schema), `lib/seed.ts` (demo data) |
| ML pipeline | `ml/waste/01_waste_model.ipynb`, `ml/matching/02_matching_model.ipynb` (Python, offline) → `lib/model/waste-models.json`, `lib/model/matching-model.json` |
| ML inference | `lib/ml/runtime.ts` (tree/linear/KNN evaluator), `lib/ml/waste.ts`, `lib/ml/matching.ts` |
| Data warehouse | `ml/warehouse/` — DuckDB star schema for waste and rescue analytics (offline, `npm run warehouse`) |
| AI assistant | `rag/` (Python: knowledge base, sqlite-vec + FTS5, LangGraph agent, local-model eval), `lib/rag/search.ts` + `app/app/assistant` (web) |
| Automation | `lib/automation.ts` (events) → n8n workflow in `automation/n8n/` → `app/api/integrations/n8n` |

**Donation workflow:** Available → Requested → Accepted → Scheduled → Collected → Delivered, plus Cancelled / Expired / Rejected / Failed Collection. Transitions are validated on the server, every change records actor and time, and acceptance runs in a transaction so only one recipient can claim a donation.

**Matching:** safety rules first (verified, accepts the category, has the storage, can receive before the deadline, has capacity), then the AI model ranks the remaining organizations by the estimated probability of a successful delivery. If the model is unavailable, a transparent weighted rule score (capacity 30%, distance 30%, timing 20%, need 20%) is used instead. Each match comes with an explanation.

## Machine learning

### 1. Predicting leftovers (real Kaggle data)

- **Data:** `ml/waste/data/raw/food_waste_dataset.csv` (8,000 rows, 4 business types, 6 food categories).
- **Preprocessing:** leakage columns removed (`Units_Sold`, `Remaining_Stock`, `Daily_Demand`, `Waste_Quantity`, `Waste_Reason`, `Donation_Made`); chronological 70/15/15 split; train-only imputation; outliers kept with a log transform; engineered expected demand / overstock features plus **spoilage features** (share of leftovers that usually spoil, by category × shelf life, temperature and weather — learned from past days only); one-hot encoding; scaling only for LR/KNN.
- **Model choice:** every model is tuned and compared by **accuracy over 5 rolling time periods** inside train+validation; the test period is used once at the end.
- **Leftover amount (regression):** Gradient Boosting, test MAE **7.82 units**, R² **0.915**, 80% range covers 81.4% of test days. Mean baseline MAE 22.7. A historical-average rule is equally strong (MAE 7.77) — reported honestly.
- **Waste risk Low/Medium/High (classification):** Random Forest (300 trees), accuracy **71.2%** (v1: 69.4%; always-“Low” baseline 53.3%), macro precision 0.690, recall 0.643, F1 0.660, ROC-AUC 0.859. XGBoost and LightGBM were also tried (70.9% / 70.6%). Confusion matrix and per-class report: `ml/waste/reports/` and the Admin → AI model page.
- **Why not higher:** the waste level depends on how many customers actually come that day, which is unknown in the morning. Even a model told the real leftover amount would only reach ~88%. The data has no day-to-day pattern (autocorrelation ≈ 0), so history/lag features do not help.

### 2. Finding the right organization (SYNTHETIC data — labelled as such)

- **Data:** `ml/matching/data/synthetic_donation_matching_dataset.csv` (12,424 rows, 2,500 donations × 60 fictional organizations), generated by `generate_matching_dataset.py` and anchored on Kaggle rows. Deliberately messy (duplicates, mixed formats, missing values, 2% label noise). Data dictionary included.
- **Model:** Gradient Boosting (class-balanced), selected on validation ROC-AUC. Test accuracy **81.1%**, precision 0.733, recall 0.842, F1 0.784, ROC-AUC **0.877**.
- **Ranking test:** top pick succeeds 75.3% (AI) vs 75.6% (rules) vs 73.2% (nearest) vs 70.2% (random). Because the data is synthetic, these numbers show the pipeline works; they are not real-world evidence.

### Serving and checks

Models are trained in the notebooks, exported to JSON and evaluated in TypeScript (no Python at runtime). `npm run test:parity` checks that TypeScript reproduces scikit-learn's outputs (`lib/model/*-golden.json`); the current max difference is below 0.00001.

Retrain: open the two notebooks in Jupyter (`pip install pandas numpy scikit-learn imbalanced-learn xgboost lightgbm matplotlib seaborn nbformat nbclient`) and run all cells.

## Data warehouse (DuckDB)

An analytics warehouse, separate from the app's transactional SQLite database, built with **DuckDB** as a star schema:

| Table | Grain / content | Source |
|---|---|---|
| `fact_inventory_waste` | one inventory item per day: bought, sold, wasted, waste level | Kaggle CSV (8,000 rows) |
| `fact_donation_match` | one donation offered to one organization: distance, accepted, delivered | synthetic CSV (12,272 rows after cleaning) |
| `fact_app_donation` | one donation listed in the app, with its delivery | the app's database `data/foodsphere-v2.db` (optional) |
| `dim_date`, `dim_food_category`, `dim_business_type`, `dim_weather`, `dim_waste_reason`, `dim_area`, `dim_organization` | shared dimensions | all sources |

```bash
npm run py:setup     # once: Python packages into .venv
npm run warehouse        # builds data/foodsphere_warehouse.duckdb and ml/warehouse/reports/*.csv
```

- Schema with primary and foreign keys: `ml/warehouse/schema.sql`. Analytics queries: `ml/warehouse/analytics.sql` (each result is saved as a CSV in `ml/warehouse/reports/`).
- The synthetic data is cleaned with the same function the matching model uses, so the warehouse and the model see identical data. Every fix is counted in `reports/summary.json`.
- The app database is read from a temporary copy, so the warehouse never changes it.
- Example findings: overall waste rate 4.88%; Prepared Food wastes the most (7.61%); food banks complete 69.9% of offers vs 25.1% for shelters; pickups under 2 km succeed 42.4% of the time vs 25.0% at 10 km or more (synthetic data).

## Ask FoodSphere (RAG assistant, LangGraph, local models)

Every role has **Ask FoodSphere** in the sidebar. It answers questions about donations, food safety, roles, privacy and the AI models **only from FoodSphere's own documents**, cites its sources, and says when the documents do not cover a question.

| Technique | How it is done | Where |
|---|---|---|
| Knowledge base | 11 documents generated from the app's own pages, FAQ, help guides, README, model results and warehouse findings | `rag/build_knowledge.py` → `rag/knowledge/` |
| Naive RAG | heading-aware chunks (~700 characters, 1-sentence overlap) → embeddings → nearest neighbours | `rag/common.py`, `rag/ingest.py` |
| Contextual RAG | each chunk gets 1–2 sentences situating it in its document, written by a local LLM with Anthropic's contextual-retrieval prompt (cached in `rag/context_cache.json`; rule-based context without Ollama) | `rag/ingest.py` |
| Vector database | **sqlite-vec** (`vec0` tables, cosine) in `data/rag.db` | `rag/ingest.py`, `rag/retrieve.py` |
| Hybrid search | SQLite **FTS5** keyword search (BM25) + vector search, fused with Reciprocal Rank Fusion | `rag/retrieve.py`, `lib/rag/search.ts` |
| Agent | **LangGraph**: retrieve → grade (are the question's words covered?) → generate, or widen the search once, then refuse | `rag/agent.py` |
| Local models | **Qwen 2.5 1.5B, Llama 3.2 1B, DeepSeek-R1 1.5B, Mistral 7B** through Ollama; embeddings with nomic-embed-text | `rag/eval.py` |

The live website cannot reach a model on your computer, so it uses the same flow in TypeScript with LSA embeddings (built from the corpus, no download) and answers by quoting the best sentences. `npm run test:rag` checks that the TypeScript search returns exactly the Python results. When `OLLAMA_URL` is set (local development), the web app uses a local model to write the answer.

### Run it with the local models (Mac/Windows/Linux)

1. Install [Ollama](https://ollama.com/download), open it once, then pull the models (about 8 GB):
   ```bash
   ollama pull qwen2.5:1.5b && ollama pull llama3.2:1b && ollama pull deepseek-r1:1.5b && ollama pull mistral:7b && ollama pull nomic-embed-text
   ```
2. Set up Python once (creates a private `.venv` folder in the project) and run everything:
   ```bash
   npm run py:setup
   npm run rag:all      # rebuild the knowledge base, LLM contexts, embeddings, then evaluate retrieval + all 4 models
   ```
   Results: `rag/reports/eval_report.md` (retrieval hit@1/hit@3/MRR for naive vs contextual and vector vs keyword vs hybrid, then answer accuracy, citations, refusals and speed per model).
3. Ask from the terminal: `npm run rag:ask -- "How cold must refrigerated food be kept?" --model mistral:7b`
4. Use a local model in the web app: add `OLLAMA_URL=http://localhost:11434` and `OLLAMA_MODEL=qwen2.5:1.5b` to `.env.local`, then `npm run dev`.

## Workflow automation (n8n)

Important donation events are sent to a self-hosted **n8n** workflow (`automation/n8n/foodsphere-alerts.workflow.json`):

```
FoodSphere event (webhook) → Check secret & write alert (code) → Urgent? ─yes→ Notify admins in FoodSphere (HTTP → /api/integrations/n8n)
                                                                        └no──→ Log only
```

- Events: `donation.created`, `donation.deadline_soon` (2 hours left), `donation.expired`, `collection.failed`, `donation.delivered`. They are sent only after the database change has been saved, and never block the app if n8n is down.
- Urgent events come back as **[n8n] notifications for every administrator** and are recorded in the audit log. Both directions are protected with a shared secret.
- Run it locally (no install needed, n8n is downloaded on first use):
  ```bash
  npm run n8n          # terminal 1: creates the secret in .env.local, imports + activates the workflow, starts n8n on http://localhost:5678
  npm run dev          # terminal 2
  ```
  Then **Admin → Platform Settings → Workflow automation → Send test event**. The editor at http://localhost:5678 shows every run.

## Deploy (Vercel + Turso)

Locally the app uses a SQLite file in `data/`. Online it uses **Turso** (hosted SQLite) whenever these two environment variables are set: `TURSO_DATABASE_URL` and `TURSO_AUTH_TOKEN`.

1. **Turso:** create a database at turso.tech, then copy its URL (`libsql://…`) and create a database token.
2. **Vercel:** in the project folder run `npx vercel` (sign in when asked), then add the two variables with `npx vercel env add TURSO_DATABASE_URL` and `npx vercel env add TURSO_AUTH_TOKEN` (choose Production, Preview and Development), then run `npx vercel --prod`.
3. The first build (`npm run vercel-build`) creates the tables and demo data in Turso automatically; later builds keep existing data.

Files not needed online are listed in `.vercelignore`.

## Tests

- leftover forecasting and horizon validation
